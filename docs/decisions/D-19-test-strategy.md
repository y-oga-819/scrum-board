## 層の設計

完了条件が「設計判断が実装に落ちたか」を問う形になっている以上、検証も
**速いテストと正確なテストを分ける**必要がある。同じ層に混ぜると、遅いテストに
引きずられて誰も回さなくなるか、速さのために本当に確かめたいことを落とすかの
どちらかになる。

| 層 | 対象 | DB | 速度 | 実行 |
|:---:|:---|:---|:---|:---|
| **1** | 不変条件 I-1〜I-7（単一バリデーション関数） | 不要 | ミリ秒 | 毎PR |
| **2** | API（FastAPI TestClient／認可／状態遷移） | フェイク | 秒 | 毎PR |
| **3** | Cosmos契約（後述の4点のみ） | エミュレータ | 分 | 毎PR |
| **4** | E2E（主要フロー） | エミュレータ | 分 | mainマージ時 |

### 層1 — 不変条件

I-1〜I-7 は純粋関数に集約される（B-20 の完了条件）。DBもHTTPも要らないため、
**テーブル駆動で網羅する**。ここが最も安く、最も価値が高い。

「`status != 'done'` なのに `completedAt` が入っている」「`taskType='team'` なのに
`pbiId` がある」といった組み合わせを表で列挙し、期待する棄却理由まで含めて検証する。

### 層2 — API

認証（V-1〜V-4）は**テスト用の鍵ペアを生成し、JWKSエンドポイントをスタブして
検証ロジック自体を試験する**。実テナントに接続しない。改ざん署名・`aud` 不一致・
`iss` 不一致・`scp` 欠落の4つを、それぞれ独立に401になることを確認する。

### 層3 — Cosmos契約テスト（ここだけCosmosが要る）

**フェイクで通っても本番で壊れる領域だけを置く。** それ以外を入れると層3が肥大し、
CIが遅くなって層1・2の価値まで落とす。

| 検証対象 | なぜフェイクでは代替できないか | 関連PBI |
|:---|:---|:---|
| `_etag` / `If-Match` / **412** | 同時更新の検出はサーバー側の挙動 | B-07, B-23, B-26 |
| **トランザクショナルバッチ**の原子性 | 部分適用されないことは実装依存 | B-07, B-25 |
| `ORDER BY rank, id` の並び | 下記の通り**実サービスでの確認が別途必要** | B-16 |
| インデックス除外パスのRU削減 | RU実測値は実サービス／エミュレータでしか出ない | B-07, B-31 |

### 層4 — E2E

主要フローを網羅する。最低限、次を通す。

1. サインイン → PBI作成 → タスク追加
2. プランニング（PBIをスプリントへ／**タスク0件なら「タスク分解」生成**）
3. ボード操作（todo → doing → done）
4. スプリント終了（**完了タスクが動かず、未完了だけ持ち越される**）
5. スプリントから外す（チームタスクが「未割当」に現れ、**消えない**）

5番目は提案書が「唯一許容できない失敗」と呼ぶ状態（D-16）の回帰テストにあたる。

## 残存リスク — 照合順序はエミュレータで確認しない

Cosmos DB Emulator と実サービスで文字列の照合順序が異なった場合、
**「エミュレータでは通ったが本番で並びが静かに壊れる」**という、提案書が最も警戒する
失敗（06章・Q-1）がそのまま起きる。テストが通っていることが誤った安心につながるため、
何もテストしないより悪い。

したがって次のように分ける。

- **日常のCI**: エミュレータで回す。速度と無料を取る
- **Q-1 の検証**: **実サービスに10件ほど投入し、`ORDER BY` が辞書順と一致することを確認する**。
  これは B-16 の完了条件であり、**一度きりの独立したゲート**として扱う。CIには載せない
- 一致しなければ、提案書の方針どおり**浮動小数＋定期リバランスに切り替える**

エミュレータ採用の代償はこの一点に集約される。集約できているので受け入れる。

## 設計への含意

テスト戦略から、実装側に3つの要件が導かれる。**これらは後から入れると全面改修になる**ため、
該当PBIの設計時点で織り込む。

| # | 要件 | 理由 | 反映先 |
|:---:|:---|:---|:---|
| 1 | **Repositoryをポートとして抽象化し、フェイク実装を差し替えられること** | 層1・2をCosmosなしで回すため。これが無いと全テストが層3になり、CIが分単位になる | B-07 |
| 2 | **「今日」を注入可能にすること**（クロックの抽象化） | 営業日マーカー（B-24）とスプリント期間・終了処理（B-25）はテストで日付を固定できないと検証できない | B-24, B-25 |
| 3 | **seeding がスクリプト化され冪等であること** | E2Eで主要フローを網羅するには、テストごとに既知の初期状態を作り直す必要がある。手動投入では回らない | B-08 |

3番目は、E2Eの範囲を「主要フロー網羅」にした結果として **B-08 の要求が上がった**もの。
seeding は「初回に一度やる作業」ではなく「テストのたびに走る仕組み」になる。

## CI構成

```
PR:
  lint
  層1 単体（pytest / vitest）        ← 数秒
  層2 API（フェイクRepository）       ← 数十秒
  層3 Cosmos契約（エミュレータ起動）   ← 数分
  → いずれか失敗でマージブロック

main マージ時:
  上記すべて + 層4 E2E（Playwright）
```

エミュレータは起動に1〜2分かかり、TLS証明書の取り込みとヘルスチェック待ちが要る。
**起動待ちを固定 sleep で書かないこと** — CIの不安定さの典型的な原因になる。
ready エンドポイントをポーリングする。

## カバレッジ方針

**数値目標を置かない。** 代わりに**対象ベースで合意する**。

> **次の4領域はテスト必須。それ以外は書き手の判断に委ねる。**
> 1. 不変条件 I-1〜I-7
> 2. 認証検証 V-1〜V-4
> 3. rank（並び替え）
> 4. 認可（メンバー判定・403）

カバレッジ率という代理指標で縛ると、率を上げるためだけのテスト（getterの実行など）を
誘発し、**数字は上がるが壊れ方は検出できない**状態になる。これは提案書が進捗表示について
述べた「警告を避けるための数字合わせ」（05章）と同じ構造である。事実を見せ、判断は
書き手に返す（**P-1**）。

## 却下した案

| 却下した案 | 理由 |
|:---|:---|
| 全テストを実Cosmosに対して書く | 毎PRが分単位になり、誰も回さなくなる。層1が最も価値が高いのに最も回されなくなる |
| 全テストをフェイクで済ませる | 412・トランザクショナルバッチ・照合順序という**壊れると発見が遅れる領域**が丸ごと無検証になる |
| 照合順序の検証もエミュレータで行う | 実サービスと挙動が異なった場合、テストが通ることが誤った安心になる。何も試験しないより悪い |
| カバレッジ率に下限を設ける | 率を上げるためのテストを誘発する。指標が目標になると指標として機能しなくなる |
| Karma / Jasmine | 非推奨化が進んでおり、新規採用する理由がない |
