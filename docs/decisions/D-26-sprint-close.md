# D-26 スプリント終了処理（持ち越しの規則と移動先）

- **対応PBI**: [B-25](../progress.md)
- **関連**: 提案書 07章（スプリント終了処理・主要クエリ）、[D-20](./D-20-api-conventions.md)（読み書き非対称・専用エンドポイント・`If-Match`）、[D-08](../progress.md)（PBI はスプリント参照を持たない）、不変条件 **I-5**（完了タスクは持ち越し・除外の対象にしない）、設計原則 **P-1**（ルールで縛らず事実を見せる）、[D-13](../progress.md)（警告色を使わない）
- **決定日**: 2026-08-06
- **論点**: スプリントを締めるとき、(1) 未完了タスクの**移動先**をどう決めるか、(2) プレビューと確定をどう分けるか、(3) 「締められる」条件は何か。

---

## 決定

| 項目 | 決定 |
|:---|:---|
| 持ち越しの規則 | このスプリントの**未完了タスク**（`status != 'done'`）だけを次スプリントへ移す。**完了タスクは動かさない・`sprintId` を変更しない**（I-5。完了地を凍結する）。提案書 07章の 2 更新に一致 |
| 移動先 | **クライアントが既存の別スプリント（`nextSprintId`）を指定する**（提案書 07章 `sprintId = <nextSprintId>`）。自動で新規作成しない・`null`（バックログ行き）にもしない——「外す」（B-22）が `null` 戻しを既に担う。両者を区別する |
| プレビューと確定 | **`GET .../close/preview`（持ち越し一覧・読み取りのみ）と `POST .../close`（確定）を分ける**（D-20）。頻度は低いが取り返しのつかない操作なので、事実を見せてから確定する（P-1） |
| 締められる条件 | 締められるのは **`active` のスプリントだけ**（`planned` / `closed` は 422）。状態機械 `planned → active → closed`（B-21）と揃える |
| 移動先の妥当性 | 移動先が締める対象と**同じ**／既に **`closed`** なら 422（自己持ち越し・終了済みへの持ち越しを塞ぐ）。実在しなければ 404 |
| `If-Match` | **取らない**。分割（B-19）・プランニング（B-22）と同じく、複数ドキュメントを1規則で束ねて動かす**サーバー所有のドメイン操作**であり、クライアントが版を持つ単一リソースの更新ではない（個々の楽観排他はデータ層が読み直した `_etag` で内部的に満たす） |
| PBI の完了刻印 | **この操作では触れない**。`completedSprintId`（I-7）は PBI が `done` になるときの話で、終了処理とは別（提案書 05章・ベロシティ B-30 が所有）。終了処理はタスクの `sprintId` とスプリントの `status` だけを動かす |

---

## なぜ「移動先をクライアントが指定する」のか

提案書 07章の SQL は `sprintId = <nextSprintId>` と**既存の次スプリント**を指しており、
`null`（＝バックログへ戻す「外す」B-22）とは明確に区別している。だから終了処理の持ち越しは
「次スプリントへ」であって「バックログへ」ではない。

「次スプリント」を**自動で新規作成**すると、人の知らないところでスプリントが生まれ、期間も
ゴールも未定のまま走り出す（P-2「管理コストを下げる」に見えて、実際は「意図しないものが
増える」）。逆に締めるたびに人が移動先を選べば、**どのスプリントで続きを回すか**という判断が
人の手に残る（P-1）。通常の運用では「次スプリントを1つ作ってから今のを締める」——スクラムの
ケイデンスそのもの——になり、`planned` の次スプリントへ未完了が流れ込む。

移動先が無い（候補ゼロ）ときは確定させず、「先に次スプリントを作成してください」と促す。
締める側で勝手に作らないことで、`null` 戻し（外す）と次スプリントへの持ち越しという 2 つの
経路が**混ざらない**。

## なぜ「プレビューと確定を分ける」のか

提案書 07章が「『スプリントを終了』を押した時点で持ち越される一覧をプレビュー表示してから
確定する。強制も警告もせず、事実だけを見せる（P-1）」と明記している。これを D-20 の
**読み書き非対称**（頻度の低い操作に複雑さを寄せる）に乗せ、`GET .../close/preview`
（読み取り・副作用なし）と `POST .../close`（確定・副作用あり）に分けた。プレビューは
「何が次へ移るか」という**事実**だけを返し、判断（本当に締めるか・どこへ移すか）は人に返す。

## なぜ「締められるのは active だけ」なのか

状態機械は `planned → active → closed` の一方向前進（B-21）。`planned` を飛ばして `closed` に
するのは「一度も回っていないスプリントを終了扱いにする」ことで、状態機械の隣接に反する
（`is_valid_transition(planned, closed)` は偽）。既に `closed` のスプリントを再度締めるのも
意味を持たない。したがって終了処理は **active のときだけ**受け付け、それ以外は 422 で弾く。
ボードには `planned` のとき「スプリントを開始」（`active` へ）を出し、`active` のとき
「スプリントを終了」を出す——M5 の「スプリントが1周回る」を開始から終了まで一筆で辿れる
ようにする。

## I-5 をどこで担保するか

I-5（完了タスクは持ち越し・除外の対象にしない・`sprintId` を変更しない）は**単一文書では
表せない操作級の不変条件**で、B-20 の `check_invariants`（単一文書の I-1〜I-4）には載らない。
プランニングの「外す」（B-22）が未完了だけを `null` に戻したのと**同じ切り分け**で、終了処理は
未完了だけを次スプリントへ移す。両操作とも `status != 'done'` でフィルタする 1 か所
（`app/data/sprint_close.py` / `app/data/planning.py`）に閉じ、完了タスクの `sprintId` を
凍結する。

## 実装の形

- **データ層** `app/data/sprint_close.py` — `carry_over_targets`（プレビュー用・読み取り）と
  `close_sprint`（未完了の `sprintId` 付け替え＋スプリント `status=closed`）。純粋にドメインの
  語彙だけを扱い、HTTP を知らない。
- **API 層** `app/api/sprint_close.py` — `GET .../close/preview` と `POST .../close`。認可
  （`require_member`）・実在確認（404）・締められる状態か（422）・移動先の妥当性（404/422）・
  HTTP 翻訳だけを担う。`If-Match` は取らない。
- **フロント** `frontend/src/app/board/` — ボードに「開始」「終了」を状態で出し分け、終了は
  プレビュー→移動先選択→確定。締めた後は持ち越し先を表示スプリントにして、移った未完了
  タスクをそのまま見せる。件数の通知は中立色（警告色を使わない — D-13）。

タスクの移動とスプリントの締めは**順に** `replace` する（原子的バッチではない）。実 Cosmos
のトランザクショナルバッチ（提案書 09章・同一パーティション）による原子化は層3（B-11）／
実サービス（B-31）に回す（プランニングが順次 `replace` で書いているのと揃える）。
