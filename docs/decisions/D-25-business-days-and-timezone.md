# D-25 進捗マーカーの営業日の定義とタイムゾーン

- **対応PBI**: [B-24](../progress.md)（進捗表示）
- **関連**: 提案書 [05章](../proposal.html)（2本バー・「経過営業日 ÷ 総営業日」）、設計原則 **P-1**（ルールで縛らず、事実を見せる）・**P-2**（管理コストを下げる）、[D-13](../progress.md)（警告色を使わない）、[D-19](./D-19-test-strategy.md)（「今日」を注入して固定できる）
- **決定日**: 2026-08-06
- **論点**: B-24 の完了条件が「（要確認）祝日・タイムゾーンの扱いを決めた」と保留していた。マーカー位置は**経過営業日 ÷ 総営業日**（提案書 05章）で、暦日で数えると週末に必ず遅れて見えるため営業日で数える。では「営業日」に**日本の祝日**を含めるか、そして「今日」はどのタイムゾーンの暦日か。

---

## 決定

| 項目 | 決定 |
|:---|:---|
| 営業日 | **平日（月〜金）かつ日本の祝日でない日**。土日に加えて**日本の祝日も除外**する |
| 祝日の判定 | [`jpholiday`](https://pypi.org/project/jpholiday/) に委譲する（**振替休日・国民の休日**を含む。春分／秋分・ハッピーマンデーも算出）。祝日テーブルを自前で持たない |
| タイムゾーン | 「今日」は **Asia/Tokyo の暦日**で数える（`app.data.clock.jst_date`）。保存は従来どおり UTC（`isoformat_utc`）で、これは「今日はいつか」を決めるためだけに使う |
| 経過営業日 | `startDate` から `min(today, endDate)` までの営業日数（**両端含む**）。`today < startDate` なら 0、`today >= endDate` なら総営業日数に張り付く（区間 [0, total] に収める） |
| 期間未設定 | `startDate` / `endDate` の片方でも未設定なら営業日は **`null`**。フロントはマーカーを描かない（ありもしない位置をでっち上げない — P-1） |
| 「今日」の注入 | `compute_progress` は純関数で `today` を引数に取り、`GET /board` は `get_clock`（`app.state.clock`）から供給する。**固定してテストできる**（D-19） |

---

## なぜ祝日も除外するのか

マーカーは「このペースで計画通り終わるか」を読むための計器で、**経過の分母は人が働く日**で
なければ意味が合わない。土日を除くのに祝日を残すと、祝日の翌営業日にマーカーが実態より
先へ飛び、「遅れている」と誤読させる。日本のチームのスプリントを前提にするので、祝日も
営業日から外す。

## なぜ `jpholiday` に委譲するのか（自前計算しない）

日本の祝日は**固定日だけではない**。春分／秋分の日は天文計算、成人の日・海の日などは
ハッピーマンデー（第 N 月曜）、日曜と重なった祝日の**振替休日**、2 つの祝日に挟まれた日の
**国民の休日**——これらを自前で実装すると 1 日静かにずれる余地が多い。順序が静かに壊れる
ランク生成をライブラリに委ねた（[B-16](../progress.md)）のと同じ判断で、実績ある実装に寄せる。

## なぜ Asia/Tokyo 固定なのか

`SystemClock` は UTC を返すため、そのまま日付にすると日本時間の深夜〜朝（UTC では前日）で
「今日」が 1 日ずれる。朝会は日本時間の朝に開くので、その時刻に「今日」が正しく当日で
あることが要る。テナントやユーザーごとのタイムゾーン設定は**まだ持たない**（P-2）。単一
チーム・単一タイムゾーンで運用している間はこれで十分で、複数タイムゾーンの要求が実際に
出てきたら、そのとき product か user にタイムゾーンを持たせて見直す。

## やらないこと（P-1 / D-13 の再確認）

営業日で数えても、**マーカーより先端が左だから警告色にする、といったことはしない**。
マーカーとバー先端の位置関係という**事実**を見せるだけで、遅れの判断はチームに返す
（提案書 05章「やらないこと」・D-13）。営業日の除外はマーカーの**位置の正確さ**の話であり、
そこに規範的な色や強制を足すものではない。
