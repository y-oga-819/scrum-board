## 認証を最初に実証する

**本プロジェクトの主題は「Easy Authを使わないEntra IDの認証・認可」のPoCである。**
スクラムバックログ管理アプリは、そのPoCを実地で回すための題材を兼ねている。

したがって**最も不確実な部分を最初に検証する**順序を取る。Entra IDのアプリ登録は
**設定漏れが後の工程で分かりにくい形で表面化する**（提案書08章）類の作業であり、
後回しにする理由がない。

### 認証と認可をデータ層の要否で分ける

順序設計の要点はここにある。

| | 必要なもの | 何を実証するか |
|:---|:---|:---|
| **認証**（B-05・B-06） | **データストア不要** | Easy Authを使わずMSAL＋JWT検証で通ること |
| **認可**（B-14・B-27） | データ層が要る（`member` をCosmosに持つ） | メンバー判定・403・ブートストラップ |

認証だけなら **B-03 → B-01 → B-05 → B-06 の4つで完結**し、Cosmos もマイグレーションも
要らない。しかもローカル（`localhost:4200` のリダイレクトURI）だけで検証できる。
**PoCの核心に最短で到達できる。**

```
M1  認証PoC   B-03 骨格(1ページ) → B-01 Entra登録 → B-05/B-06 → B-02/B-04 でデプロイ確認
M2  認可PoC   B-07 データ層 → B-26 マイグレーション → B-14 認可 → B-27 ブートストラップ
M3〜 アプリ本体の作り込み
```

**M2 完了時点でPoCは完成する。**

### ユーザー解決をポートとして切り出す

「現在のユーザーは誰か」を解決する責務を**単一の依存**として切り出す。

```
現在ユーザーの解決（ポート）
  ├─ Entra ID 実装 : トークンを検証（V-1〜V-4）し oid から user を引く   ← 本番
  ├─ テスト用実装  : テスト鍵で署名したトークン／固定ユーザー            ← 層2テスト
  └─ ゲスト実装    : 固定の usr_guest を返す                            ← 任意（B-30）
```

**この抽象はテストのために必須である**（D-19 の層2はトークンをスタブして回す）。
したがって B-06 の一部として作る。ゲスト経路はそこに実装をもう1つ足すだけになる。

**分岐ではなく差し替えで表現すること。** `if guest:` をハンドラに撒くと、
実装を増やすたびに全ハンドラを触ることになる。

### ゲスト経路（B-30）の位置づけ

当初これは「認証を待たずに画面開発を始める」ための仕組みとして構想した。
**認証を先に作る順序に変えたため、その存在理由は消えた。**

残る価値は「開発時に毎回サインインしなくてよい」という利便性のみであり、
**任意の位置づけに格下げする。不要なら落としてよい。**

| 制約（採用する場合） | 内容 |
|:---|:---|
| **対象** | **サンドボックスのみ**。本番プロジェクトには一切アクセスできない |
| **有効化** | 環境変数で制御。**本番では既定でOFF** |

本番でONにすると、URLを知る誰でもサンドボックスを叩ける。データは壊してよいので
実害は薄いが、**App Service F1 の1日60 CPU分と Cosmos の無料枠を外部から枯渇させられる**。
F1 が止まれば本番プロジェクトも巻き添えになる。

## サンドボックスを一枚挟む

**鶏卵問題（B-27）を、権限を緩めずに解く。**

「メンバーでなければ403」（B-14）を素直に実装すると、最初のメンバーが存在しない状態を
抜けられない。かといって「最初にサインインした人を自動的に admin にする」と、
実行順で admin が決まり、同時サインイン時の競合も残る。

そこで**誰でも入れる練習場を1つ用意する**。

| プロダクト | 誰が入れるか | 位置づけ |
|:---|:---|:---|
| `prd_sandbox` | **サインインした全員が自動で `member`** | 好きにいじってよい。壊れても構わない |
| `prd_scrum_board` | **スクリプトで明示的に登録した人のみ** | このアプリ自身のバックログを管理する本番 |

これで次が同時に成立する。

- **403で詰まる経路が無い** — サインインできた人には必ず居場所がある
- **本番データは守られる** — 明示的な権限付与が要る
- **オンボーディングが自然** — 新メンバーはまずサンドボックスで触ってから本番に招かれる

サンドボックスは「壊してよい」ことに価値がある。バックログツールは**触ってみないと
使い勝手が分からない**類のもので、本番データで練習させるのは筋が悪い。

## エンティティの追加

提案書のドメインモデル（04章）に `user` を加え、`member` の役割を絞る。

| 型 | パーティション | id | 持つもの |
|:---|:---|:---|:---|
| `user` | **`_system`** | `usr_<oid>` | `oid` / `displayName` / `email` |
| `member` | 各 `productId` | `mbr_<oid>` | `userId`(=oid) / `role` |
| `migration` | **`_system`** | `mig_<version>` | `version` / `appliedAt` |

### `_system` 予約パーティションを設ける理由

`user` はどのプロダクトにも属さない。テナント内で一意の存在である。
単一コンテナ／PK=`productId` の設計を維持したまま置き場所を作るため、
**`productId = "_system"` を予約する**。

- コンテナは増えない（D-08 のコスト前提を壊さない）
- `id = usr_<oid>` なので、`oid` から**ポイントリード（約1 RU）**で引ける
- クロスパーティションクエリが発生しない

> **予約語の扱い**: `_system` は productId として払い出さない。
> プロジェクト作成機能（B-31）でもこの値を弾くこと。

### `member` をポイントリード可能にする

`id = mbr_<oid>` にすることで、**B-14 の認可チェックが毎リクエスト・ポイントリード1件**で済む。
最頻出の処理（すべてのAPIが通る）が最も安い操作になる。

`oid` をキーにするのは提案書の方針どおり（08章「メールアドレスは変わり得るのでキーにしない」）。

## マイグレーション機構

Cosmos DB はスキーマレスなので DDL は不要だが、**初期データの投入と、
後方互換なデータ変換**はバージョン管理された仕組みに載せる。

```
migrations/
  001_create_sandbox_product.py
  002_create_scrum_board_product.py
```

- 起動時（またはデプロイ時）に**未適用のものだけを順に適用**する
- 適用後に `_system` パーティションへ `mig_<version>` を記録する
- **冪等性はバージョン記録で担保**する。スクリプト自身が冪等である必要はない

`ensure`（無ければ作る）を毎回走らせる方式ではなく、バージョン記録にしたのは、
**再デプロイのたびに実データを設定値で上書きする事故**を防ぐため。
一度適用したマイグレーションは二度と走らない。

### マイグレーションが作るもの / 作らないもの

| 作る | 作らない |
|:---|:---|
| `product` ドキュメント（サンドボックス・本番） | **`member`** — 本番の権限はスクリプトで明示的に |
| 将来のデータ変換 | **`user`** — 初回サインイン時に作られる |

---

## 初回サインインのフロー

```
① トークン検証（V-1〜V-4）        → oid を得る
② _system で usr_<oid> をポイントリード
③ 無ければ user を作成           ← displayName / email はトークンのclaimから
④ 同時に prd_sandbox へ mbr_<oid> を role=member で作成
⑤ GET /api/me が user と所属プロダクト一覧を返す
```

### 競合の扱い

2つのリクエストが同時に初回サインインした場合、③④の作成が衝突する。
**`id` 重複による 409 は握りつぶして続行する**（create-if-absent と等価）。
`id` が `oid` から決定的に導かれるため、後勝ちでも同じものが1件できるだけで害がない。

### `GET /api/me`

```json
{
  "oid": "…",
  "displayName": "…",
  "isGuest": false,
  "products": [
    { "productId": "prd_sandbox",     "name": "サンドボックス", "role": "member" },
    { "productId": "prd_scrum_board", "name": "スクラムボード", "role": "admin"  }
  ]
}
```

これで4つが同時に片付く。

1. **フロントが `productId` をハードコードしない**
2. 認可判定と経路が同じになる
3. `products` が空＝**未招待ユーザーに見せる画面**の判定になる
4. **ゲストと実ユーザーで同じ形**を返せる（フロントに分岐が要らない）

## 本番プロジェクトへの登録スクリプト

```
scripts/add_member.py --product prd_scrum_board --oid <oid> --role admin
```

`oid` は `az ad signed-in-user show --query id` で引く。
B-01 で `az` CLI 中心の手順を残すと決めているので、そこに含める。

**このスクリプトは再実行可能にする**（既存なら role を更新）。
メンバーの増加で必ず再実行される（提案書 12章）。

## プロダクトが2つになることの影響

提案書 02章は「複数プロダクト横断のダッシュボード」を対象外としているが、
禁じているのは**横断ダッシュボード**であって、複数プロダクトの存在自体ではない。
パーティション設計（PK=`productId`）はむしろ複数プロダクトを前提にしている。

ただし次の追加が要る。

| 追加 | コスト | 理由 |
|:---|:---|:---|
| **プロダクトセレクタ** | 小 | D-20 で `/api/products/{pid}/…` とパスに入れてあるため、URL を変えるだけで切り替わる |

**2画面原則は壊れない。** セレクタは画面ではなくシェル（ヘッダ）の要素であり、
プロダクトバックログとスプリントという2画面構成はそのまま維持される。

## テストとの関係（D-19）

| 環境 | やること |
|:---|:---|
| 本番・開発 | 実Cosmos にマイグレーションを適用 |
| **E2E** | **エミュレータにマイグレーションを全適用 → fixtures 投入**。毎回クリーンな状態から |
| 層1・2 | フェイクRepository。マイグレーション不要 |

E2E は `prd_test_<runId>` を使って**パーティションで隔離する**。
サンドボックスは人間が触る練習場であり、E2E のデータ置き場にはしない
（テストが人間の操作で壊れる／人間の練習がテストで消える、の両方を避ける）。

**fixtures は `productId` が `prd_test_` で始まらなければ実行を拒否する。**
本番データに流し込む事故は、一度起きると復旧できない。

teardown は**物理削除**にする。論理削除（`isDeleted`）はアプリの復旧価値のための機構であり、
テストの後片付けとは目的が違う。

**E2Eは層2と同じくユーザー解決ポートを差し替えて回す。** ゲスト経路を採用するなら
それを使ってもよいが、テスト用実装があれば足りる。

## role の粒度

**`admin` / `member` の2種のみ。**

- `admin` — メンバー管理ができる
- `member` — それ以外すべて

スクラム上の役割（PO / SM / Developer）は**持たない**。
アプリの振る舞いが何も変わらないため実質メタデータであり、
必要になったら後から追加してもデータの履歴を失わない（**P-3**）。

**共同管理者（B-32）も新しい role を必要としない。** `admin` を複数人に付けるだけで表現できる。

## 将来 — プロジェクト管理機能（B-31 / B-32）

優先度は低い。**アプリ基盤と認証を固め、スクラム機能を作り込むほうが先**。
ただし方向性だけ記録しておく。

| 機能 | 対応 |
|:---|:---|
| ユーザーがプロジェクトを作成できる | `product` を作り、作成者を `admin` として登録。`_system` を予約語として弾く |
| 作成者が他ユーザーを招待できる | 対象ユーザーの `member` を作る |
| ユーザーが参加申請できる | **`joinRequest` 型を追加**（`productId` / `userId` / `status`） |
| 作成者が承認・拒否できる | `joinRequest.status` を更新し、承認時に `member` を作る |
| 共同管理者を付与できる | `member.role` を `admin` に変更（**新しい role は不要**） |

ここまで入ると、サンドボックスは「最初の1つ」以上の意味を持たなくなる可能性がある。
その時点で位置づけを見直してよい。

## 却下した案

| 却下した案 | 理由 |
|:---|:---|
| ゲスト経路を先に作り、認証を後回しにする | **プロジェクトの主題を最後に回すことになる。** 最も不確実な箇所の検証が遅れ、Entra IDの設定漏れが後工程で表面化する |
| ゲスト経路を `if guest:` の分岐で実装する | 分岐がハンドラ全体に散り、実装を増やすたびに全ハンドラを触ることになる。**差し替えで表現する** |
| ゲスト経路を本番でも有効にする | 無料枠を外部から枯渇させられる。F1が止まれば本番プロジェクトも巻き添えになる |
| ゲストに本番プロジェクトを読ませる | サンドボックスと本番を分けた意味が消える |
| 初回サインイン者を自動的に `admin` にする | 実行順で admin が決まる。同時サインイン時の競合が残る |
| `productId` を環境変数で1つに固定する | サンドボックスと本番を分けられない。オンボーディングの居場所が作れない |
| 毎起動で `ensure`（無ければ作る）を走らせる | 実データを設定値で上書きする事故が起きうる。バージョン記録なら二度と走らない |
| `user` を各プロダクトに複製する | 表示名の更新が全プロダクトに伝播しない。テナント内で一意の存在を複数持つ理由がない |
| `user` 用に別コンテナを作る | コンテナごとに最低400 RU/s。無料枠を圧迫する（D-08） |
| スクラム上の役割を `role` に持つ | アプリの振る舞いが変わらない。後から追加できる（P-3） |
| 共同管理者用に新しい role を作る | `admin` を複数人に付ければ表現できる |
