# D-27 デイリーノートのキーと取得（1日1件・get-or-create）

- **対応PBI**: [B-27](../progress.md)
- **関連**: 提案書 04章（`dailyNote` の共通フィールド・**1日1ドキュメント**）、05章（デイリーパネル）、[D-20](./D-20-api-conventions.md)（読み書き非対称・`If-Match` 必須・単一ドキュメント応答は `ETag`）、[D-24](./D-24-optimistic-concurrency-ux.md)（412 発生後は黙って上書きせず再取得）、[D-21](./D-21-bootstrap-and-migration.md)（決定的 ID・create-if-absent・409 握りつぶし）、設計原則 **P-3**（後から復元できない情報だけを先に持つ）
- **決定日**: 2026-08-07
- **論点**: デイリーノート（`dailyNote`）を、(1) **何を鍵に「1日1件」**を担保するか、(2) パネルを開いたとき**どうやって編集対象を得る**か（存在しない日をどう扱うか）、(3) 同時編集の競合をどう扱うか。

---

## 決定

| 項目 | 決定 |
|:---|:---|
| 1日1件の担保 | **決定的 ID `dly_<sprintId>_<date>`** のポイントリードで担保する（`mbr_<oid>` / `usr_<oid>` と同じ発想 — D-21）。連番 ULID を振らないので、同じ (sprint, date) には**構造的に1件しか作れない**（重複は 409） |
| スコープ | **(スプリント, 日付)** で鍵る（プロダクト×日付ではない）。パネルは画面B（ボード）の選択スプリントに対して開くため、URL も `/sprints/{sid}/daily/{date}` の下に**ネスト**する（`planning` / `board` / `close` と同じ）。表示スプリントを切り替えれば、そのスプリントのその日のノートを見る |
| 取得 | **`GET .../daily/{date}` は get-or-create**（無ければ空のノートを1件作って返す・冪等）。パネルは常に**編集対象と版（`ETag`）を持てる**。作成が同時実行で衝突しても 409 を握りつぶして読み直す（onboarding の `ensure_bootstrapped` と等価 — D-21） |
| 編集 | **`PATCH .../daily/{date}`（`If-Match` 必須）**。`agenda` / `minutes` を部分更新する。汎用 `PATCH`＋`ETag` の既定の道に乗せ、書き込みに専用経路を新設しない（B-18 の PBI 詳細と同型） |
| 同時編集 | 楽観排他（`If-Match` / 412）。**1日1件にしたのは「肥大化と競合を減らす」ため**（提案書04章）で、競合をゼロにはしない。版がずれたら黙って上書きせず最新を読み直す（D-24） |
| アジェンダ項目の id | **クライアントが採番**する（不透明な識別子。B-18 の完了条件チェックリストと同じ）。空文字の項目は保存時に落とす |
| 日付の検証 | `{date}` は **`YYYY-MM-DD`（ISO 8601）** のみ受ける（不正な形は 422）。スプリント期間内かは**問わない**——朝会は期間外の日に開くこともあり、事実を縛らない（P-1） |

## なぜ「決定的 ID `dly_<sprintId>_<date>`」なのか

提案書04章は `dailyNote` を「スプリント単位ではなく**1日1ドキュメント**」と定め、その狙いを
「議事録の追記でドキュメントが肥大化し、同時編集の競合が増えるのを避けるため」と書く。すなわち
**日付が一意鍵**である。ULID を振って `date` を検索キーにすると、「1日に2件作られていないか」を
クエリで毎回確かめねばならず、競合で二重に作られる窓も残る。id 自体を (sprint, date) から
決定的に導けば、ストアの一意制約が「1日1件」を**構造的に**保証し、ポイントリード1件（約1 RU）で
引ける。認可（`mbr_<oid>`）・ユーザー（`usr_<oid>`）で採った「最頻出の取得を最も安い操作にする」
方針（D-21）と揃う。

スコープを (プロダクト, 日付) ではなく **(スプリント, 日付)** にしたのは、デイリーが特定の
スプリントの文脈で開かれるから。通常アクティブなスプリントは1つなので実運用では同じだが、
スプリントに紐付けておけば「そのスプリントのその日の議事録」を素直に辿れ、URL のネストとも一致する。
`sprintId` はドキュメント本体にも持つ（提案書04章のフィールド）。

## なぜ「GET を get-or-create」にするのか

デイリーパネルは**開いてすぐ編集できる**のが自然（アジェンダのチェック、議事録の入力）。そのためには
パネルが最初から「編集対象のノート」と「更新に載せる版（`ETag`）」を持っている必要がある。ここで
選択肢は2つ:

1. **GET は 404、初回保存で作る（PUT upsert）** — 初回だけ版が無く、クライアントが「作成」と「更新」を
   出し分ける。書き込みの `If-Match` 必須という既定（D-20）から外れ、経路が二本になる。
2. **GET が無ければ作って返す（get-or-create）** — パネルは常にノート＋版を持ち、編集はすべて
   `PATCH`＋`If-Match` の一本道。**採用**。

GET に副作用（作成）があるのは一見きれいでないが、初回サインインの `GET /api/me` が user と
サンドボックス member を作る（`ensure_bootstrapped`）のと**同じ既定パターン**であり（D-21）、
本プロジェクトでは前例がある。「デイリーパネルを開いた日のノートは実在する」という素直な意味づけで、
409（同時に開いた別リクエストが先に作った）は握りつぶして読み直す。パネルを開かなければノートは
作られない（ボードの表示だけでは作らない）ので、空ノートが無闇に増えることはない。

## なぜ書き込みに専用経路を作らないのか

デイリーノートの更新は「1件のドキュメントの `agenda` / `minutes` を書き換える」だけで、複数
ドキュメントを1規則で束ねる操作（プランニング B-22・終了処理 B-25）ではない。したがって
**単一リソースの汎用 `PATCH`＋`If-Match`**（B-15/B-18 の PBI と同型）で足り、`ETag` ヘッダで
版を返す（D-20 の単一ドキュメント応答の非対称）。新しい書き込み語彙を増やさない。

## 実装の形

- **データ層** `app/data/daily_notes.py` — `daily_note_id(sprint_id, date)`（決定的 ID）・
  `new_daily_note_data`・`get_daily_note`（ポイントリード）・`ensure_daily_note`（get-or-create・
  409 握りつぶし）。HTTP を知らない。
- **API 層** `app/api/daily_notes.py` — `GET .../daily/{date}`（スプリント実在確認→ get-or-create→
  `ETag`）と `PATCH .../daily/{date}`（`If-Match` 必須で `agenda` / `minutes` を更新）。認可
  （`require_member`）・404・422（日付形式）・HTTP 翻訳だけを担う。
- **フロント** `frontend/src/app/board/` — ボードにデイリーパネルを開く導線を足し、`DailyNoteService`
  で当日のノートを get-or-create して編集する。版がずれたら（412）読み直す（D-24）。
