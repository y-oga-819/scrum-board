# D-20 API共通規約

- **対応PBI**: [B-12](../progress.md)
- **関連**: 提案書 [Q-10](../proposal.html)、07章 主要フロー、不変条件 I-1〜I-7
- **決定日**: 2026-07-25

---

## 決定

| 項目 | 決定 |
|:---|:---|
| 読み取りAPI | **画面単位**（`/backlog`・`/board` で1往復） |
| 書き込みAPI | **リソース単位**（PBI／タスク／スプリント）＋ドメイン操作エンドポイント |
| エラー形式 | **RFC 9457 `application/problem+json`** ＋拡張メンバー `violations` |
| 楽観排他 | **`If-Match` 必須**。不一致は **412**、欠落は **428** |
| 型共有 | **OpenAPI → TypeScript 自動生成**。CIで生成物の差分を検出 |
| 信頼境界 | **サーバー**。フロントのバリデーションはUX補助 |

## 読み書きを非対称にする

**読み取りは画面の都合に、書き込みはドメインの都合に従う。両者を同じ形に揃えない。**

提案書は「ボード表示は**1クエリで完結する**。最頻出」（07章）と書いている。これを純粋な
リソースRESTで実装すると、バックログ画面が「PBI一覧 → 各PBIのタスク」の **N+1** になり、
設計意図がAPI層で失われる。App Service F1 は1日60 CPU分でスリープもあるため、往復回数は
そのまま体感に出る。

一方で書き込みまで画面単位にすると、APIがUIの変更に引きずられる。書き込みはドメインの
語彙のまま保つ。

これは提案書の「**UIとデータモデルは一致させなくてよい**」（03章）と同じ発想である。
UIとデータの間に翻訳層を置くことを認めているなら、APIもその翻訳の一部を担ってよい。

### 読み取り（画面単位）

| エンドポイント | 返すもの | 画面 |
|:---|:---|:---|
| `GET /api/products/{pid}/backlog` | PBI（`rank, id` 順）＋各PBIの配下タスク＋未割当チームタスク | A |
| `GET /api/products/{pid}/sprints` | スプリント一覧（セレクタ用の最小情報） | A/B |
| `GET /api/products/{pid}/sprints/{sid}/board` | スプリント情報＋タスク＋進捗集計（2本バーの分子分母） | B |
| `GET /api/products/{pid}/sprints/{sid}/daily?date=` | 当日の議事録＋アジェンダ＋NextAction | B（サイドパネル） |

デイリーを board から分けているのは、サイドパネルが**開いたときだけ**必要になるため。
最頻出の board を軽く保つ。

### 書き込み（リソース単位＋ドメイン操作）

```
POST   /api/products/{pid}/pbis
PATCH  /api/products/{pid}/pbis/{id}
DELETE /api/products/{pid}/pbis/{id}              # 論理削除
POST   /api/products/{pid}/pbis/{id}/split        # 分割（B-19）
POST   /api/products/{pid}/pbis/{id}/rank         # 並び替え（前後の要素IDを渡す）

POST   /api/products/{pid}/tasks
PATCH  /api/products/{pid}/tasks/{id}
DELETE /api/products/{pid}/tasks/{id}
POST   /api/products/{pid}/tasks/{id}/rank

POST   /api/products/{pid}/sprints
PATCH  /api/products/{pid}/sprints/{id}
GET    /api/products/{pid}/sprints/{id}/close/preview   # 持ち越し一覧（B-25）
POST   /api/products/{pid}/sprints/{id}/close           # 終了処理

POST   /api/products/{pid}/sprints/{sid}/pbis/{pbiId}   # プランニング：取り込み
DELETE /api/products/{pid}/sprints/{sid}/pbis/{pbiId}   # プランニング：外す

PUT    /api/products/{pid}/daily/{date}                 # 1日1ドキュメント（B-27）
PATCH  /api/products/{pid}/retro-actions/{id}
GET    /api/products/{pid}/members
POST   /api/products/{pid}/members
```

**プランニングと並び替えとスプリント終了を専用エンドポイントにしているのが要点。**
いずれも複数ドキュメントを1つの規則で同時に更新する操作であり、
汎用の `PATCH` に分解するとクライアント側に規則が漏れる。

| エンドポイント | サーバー側に閉じる規則 |
|:---|:---|
| `POST .../sprints/{sid}/pbis/{pbiId}` | 配下の未完了タスクに `sprintId` を付与。**タスク0件なら「タスク分解」を1件生成**（D-15） |
| `DELETE .../sprints/{sid}/pbis/{pbiId}` | **未完了タスクのみ** `sprintId=null`。完了タスクは動かさない（I-5） |
| `POST .../close` | 未完了タスクを次スプリントへ。完了タスクは動かさない（I-5） |
| `POST .../rank` | 前後の要素IDから文字列ランクを**サーバー側で生成**（D-18） |

### `productId` をパスに明示する

パーティションキーであり、認可の単位（B-09）でもある。単一チーム前提でも
サーバー側の暗黙解決にはしない。**全呼び出し箇所でパーティションキーが見える**ことに
価値がある。

## エラー規約

RFC 9457（`application/problem+json`）に従う。標準に乗れば形式の議論が終わる（**P-2**）。

```json
{
  "type": "https://github.com/y-oga-819/scrum-board/errors/invariant-violation",
  "title": "不変条件に違反しています",
  "status": 422,
  "detail": "taskType='team' のとき pbiId は null でなければなりません",
  "instance": "/api/products/prd_001/tasks",
  "violations": [
    { "rule": "I-4", "field": "pbiId", "message": "taskType='team' のとき pbiId は null" }
  ]
}
```

**拡張メンバー `violations` で不変条件IDを機械可読にするのが要点。**
D-19 で決めたテーブル駆動テストが「弾かれたか」だけでなく
「**どの条件で**弾かれたか」まで検証できるようになる。
`I-4` を意図したテストが `I-3` で弾かれて通ってしまう、という偽陽性を防ぐ。

| コード | 用途 |
|:---:|:---|
| **401** | 未認証・トークン不正（V-1〜V-4 の失敗） |
| **403** | プロダクトのメンバーでない（B-09） |
| **404** | 存在しない、**または論理削除済み**（存在の有無を漏らさない） |
| **409** | ドメイン競合（スプリント番号の重複など） |
| **412** | **楽観排他の失敗**（`If-Match` 不一致） |
| **422** | 不変条件違反・バリデーション |
| **428** | **`If-Match` が欠落**（下記） |

## 楽観排他の契約

提案書は「**後から入れると全API改修になる**」（06章）と書いている。最初から強制する。

- 単一ドキュメントを返す応答は **`ETag` ヘッダ**を返す
- `PATCH` / `DELETE` は **`If-Match` 必須**
- `If-Match` 不一致 → **412**
- **`If-Match` 欠落 → 428 Precondition Required**（無条件更新を許さない）

428 で弾くのは、**楽観排他を「忘れられる」状態を構造的に無くす**ため。
省略を黙って許すと、実装のどこか1箇所で更新が消える経路が残り、しかもそれは
朝会で2人が同時に触ったときにしか再現しない。

### 集約GETでのETag

`/backlog` と `/board` は複数ドキュメントを束ねるため、**応答全体のETagは意味を持てない**。
各要素の `_etag` を**アイテムのフィールドとして**返し、クライアントは更新対象の要素の
`_etag` を `If-Match` に載せる。

> 412 の応答本文に「サーバー側の最新値」を含めるかは **B-26（楽観排他のUX）で決める**。
> 再取得マージ方式を採るなら含める価値があり、再操作を促す方式なら不要。ここでは決めない。

## 信頼境界

**正はAPI。フロントのバリデーションはUX補助。**

- I-1〜I-7 は**必ずサーバーで評価**する。フロントで同じロジックを再実装しない
- ただし**導出**（またいだスプリント数、PBIが今スプリントにいるか、進捗の件数）は
  フロントで計算してよい。**導出は不変条件ではなく、二重管理にもならない**

この線引きが無いと、「フロントでも一応チェックしておこう」が積み重なって
Python と TypeScript に2つの真実が生まれ、しかもずれても気づけない。

---

## 型共有

FastAPI が出力する OpenAPI を単一の真実とし、**TypeScript 型を自動生成**する。

- 生成物はリポジトリにコミットする（差分がレビューで見える）
- **CIで再生成し、差分があれば失敗**させる。生成し忘れを検出する

手書きにしないのは、Python と TypeScript で2つの真実が生まれるため。
共有スキーマ（JSON Schema）から両方を生成する案は、ビルドが重くなる割に
FastAPI が既に OpenAPI を出せる以上、得るものが少ない。

## クエリ規約

| 項目 | 決定 | 理由 |
|:---|:---|:---|
| 論理削除 | **サーバー側で常に除外**。`includeDeleted` のようなパラメータを作らない | 除外を呼び出し側の責任にすると、いつか漏れる。復旧は将来の管理機能で扱う |
| ページング | **当面持たない** | 単一チームのバックログは数百件が上限。必要になれば continuation token を足す（後から足せる — **P-3**） |
| 並び順 | **サーバーが `ORDER BY rank, id` を保証**して返す | フロントで再ソートすると、タイブレーカーの規則が2箇所に散る（D-18） |

## 却下した案

| 却下した案 | 理由 |
|:---|:---|
| 純粋なリソースREST（読み取りも） | バックログ画面がN+1になり、「ボードは1クエリで完結する」という設計意図がAPI層で失われる |
| 書き込みも画面単位 | APIがUIの変更に引きずられる。ドメインの語彙が画面の語彙に侵食される |
| 自前のエラー形式 | 拡張のたびに設計判断が要る。標準に乗れば議論が終わる（P-2） |
| `If-Match` を任意にする | 省略できる経路が1つでも残ると、そこで更新が黙って消える。しかも同時操作時にしか再現しない |
| TypeScript型の手書き | Python と TypeScript で2つの真実が生まれ、ずれても気づけない |
| `productId` をサーバー側で暗黙解決 | パーティションキーと認可の単位が呼び出し箇所から見えなくなる |
