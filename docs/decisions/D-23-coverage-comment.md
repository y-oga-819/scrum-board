# D-23 カバレッジ PR コメントを「事実」に刷新する

- **対応PBI**: [EX-2](../progress.md)（カバレッジ可視化・横断/番号外）
- **関連**: [D-19](./D-19-test-strategy.md)（テスト戦略・カバレッジ方針 P-1・「率に下限を設ける」の却下）
- **決定日**: 2026-08-02

---

## 背景

CI は PR にカバレッジコメントを貼っていたが、内容は **「今このPRの HEAD の絶対値」だけ**
だった（backend の Lines/Branches、frontend の Statements/Branches/Functions/Lines を表にするのみ）。

これでは受け手が判断・行動できない。開示された数字を見ても、

- **元の状態** — base(main) がいくつだったか
- **変化** — このPRで上がったのか下がったのか
- **次の行動** — 何をすればよいのか

がどこにも無く、「87.5%…で、これは良いの？前より下がってる？」を各自が別途調べるしかない。
**情報を開示することで受け手の理解と行動が変わる**、という肝心の設計がされていなかった。

---

## 制約 — D-19 が数値ゲートを却下している

改善案として真っ先に浮かぶのは「patch coverage の下限」「Δ の下限」で Pass/Fail を出し、
下回ったらビルドを落とすことだ。**が、これは採れない。**

[D-19](./D-19-test-strategy.md) のカバレッジ方針は **数値目標を置かない**と明言し、
「却下した案」に **「カバレッジ率に下限を設ける — 率が目標になると指標として機能しなくなる」**
を挙げている。率で縛ると、率を上げるためだけのテスト（getter の実行など）を誘発し、
**数字は上がるが壊れ方は検出できない**状態になる。方針の核は P-1 ——**事実を見せ、判断は
書き手に返す**。

したがって本PBIは、この制約の**内側で**受け手の行動につながる情報設計を作る。

---

## 決定

| 項目 | 決定 |
|:---|:---|
| 数値ゲート | **置かない。** 率の下限・Pass/Fail・ビルド失敗はいずれも入れない（D-19 順守） |
| 出す事実 (1) | **base(main) からの Δ** — 「元の状態 → 今回どう変わったか」 |
| 出す事実 (2) | **未カバーの変更行の名指し** — 「このPRで変更したのにテストが通っていない行」 |
| 集計の実装 | **stdlib のみの Python ツール** `scripts/coverage/report.py`（`unittest` で検証） |
| base の入手 | **自前の artifact**（直近の成功した main run のレポート）。外部SaaS・サードパーティ action に依存しない |

### なぜ Δ と「未カバーの変更行」なのか

どちらも **率で縛らない事実**であり、P-1 と一致する。

- **Δ** は「上がった/下がった」を示すだけで、しきい値判定をしない。元の状態と変化を並べる。
- **未カバーの変更行**は、率という代理指標ではなく **「このPRが足すべきテスト」を行番号で名指す**。
  全体%は分母が大きく 1 PR ではほぼ動かず変化を読めないが、変更行のカバー状況は「今あなたが
  書いたコードにテストがあるか」を直接示す。しかも**変更行の中にはテスト不要な行もある**以上、
  足すかどうかの最終判断は書き手に残る——まさに「事実を見せ、判断を返す」の形になる。

patch coverage の**割合も併記する**が、これはあくまで事実の要約であって合否ではない。
コメントには ✅/❌ の判定を出さず、ビルドも落とさない。

## 実装

### 単一の Python ツールに集約

backend（coverage.py の `coverage.json`）と frontend（istanbul の `coverage-final.json`
＋ json-summary）の**両方**を 1 つのツールで正規化する。ubuntu-latest には `python3` が
標準で入るため、frontend ジョブでも **uv 不要**でそのまま走る。純粋関数（差分パース・
行カバレッジ抽出・patch 集計・整形）に切り出し、**CI を待たずローカルの `unittest` で検証**
できるようにした（`make test-scripts`・CI の backend ジョブでも実行）。

- `collect` — 生カバレッジ ＋ `git diff base...HEAD` の追加行 → 正規化レポート JSON（totals・patch）
- `render` — 現在＋base のレポート → PR コメント Markdown（Δ 列・未カバー行の `<details>`）

### base 差分は自前 artifact で

main への push 時にレポート JSON を artifact 化し、PR ではワークフロー API で
**直近の成功した main run** を引き、その artifact を baseline として取得して Δ を出す。
Codecov 等の外部 SaaS もサードパーティ action も使わない（トークン設定・供給網リスクを持ち込まない）。
初回（baseline 不在）は Δ を「初回」表示にフォールバックする。

### frontend のパス写像

Angular+Vitest の istanbul は**ビルド出力先の絶対パス**（`…/dist/test-out/<ts>/src/app/x.ts`）
でカバレッジを吐くため、単純な相対化ではソース（`frontend/src/app/x.ts`）に戻らず、
git diff と一生一致しない。`src/` セグメント以降を取り出してソースへ写像する（回帰テストで固定）。
行単位データを得るため `angular.json` に istanbul `json` レポーターを追加した。

## 却下した案

| 却下した案 | 理由 |
|:---|:---|
| patch coverage / Δ に下限を設けて Pass/Fail・ビルド失敗を出す | D-19 が明示的に却下した「率に下限を設ける」に当たる。率が目標になると指標として機能しなくなる（P-1） |
| Codecov / Coveralls など外部 SaaS に移行 | Δ・patch coverage は標準で付くが、トークン管理と外部依存・供給網リスクを持ち込む。自前 artifact で足りる |
| PR 実行のたびに base を再計測して比較 | backend/frontend のテストを二重に走らせ CI が倍遅くなる。main push 時の artifact を baseline にすれば PR 側の追加コストは取得のみ |
| 全体カバレッジ率の増減だけを見せる | 分母が大きく 1 PR ではほぼ動かず、受け手の行動につながらない。変更行の名指しが「次の一手」を直接示す |
| 従来どおり絶対値のみ | 「元の状態→変化→次の行動」が読めず、開示しても受け手の理解と行動が変わらない（本PBIの動機そのもの） |
