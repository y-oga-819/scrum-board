# スクラムバックログ管理アプリ — 開発進捗管理

> このアプリ自身でPBI管理ができるようになる（マイルストーン **M3** 到達）までの間、
> AI開発の進捗をこのファイルで管理する。設計の正はあくまで
> [`docs/proposal.html`](./proposal.html)（設計提案書）にあり、本ファイルはその
> 実装進捗のトラッカーである。

- **設計原則**（迷ったらここに戻る／提案書 01章）
  - **P-1** ルールで縛らず、事実を見せる
  - **P-2** 管理コストを下げる
  - **P-3** 後から復元できない情報だけを先に持つ
- **完了条件の考え方**（提案書 12章）: 「機能が動くか」ではなく
  **設計判断が実装に落ちたか**を確認できる形で書く。

---

## このファイルの使い方

- 各PBIは `未着手` → `進行中` → `完了` の3状態で管理する（アプリの `todo/doing/done` に対応）。
- 進捗の実体は各PBIの**完了条件チェックリスト**にある。チェックが全部埋まって初めて `完了`。
- `B-01`〜`B-24` は提案書由来のPBI。`B-00` と `B-25`以降は
  **設計レビューで抽出した着手前の欠落**を埋めるための追加PBI（末尾に判断根拠を記載）。
- 着手順を縛るのは**依存関係だけ**（提案書 12章）。`依存` 列を見て着手可能なものから進める。

### ステータス凡例

| 記号 | 状態 | 意味 |
|:---:|:---|:---|
| ⬜ | 未着手 | 未着手。依存が解けていれば着手可能 |
| 🟨 | 進行中 | 着手済み。完了条件の一部が未達 |
| ✅ | 完了 | 完了条件をすべて満たした |
| 🔒 | ブロック | 依存または未決事項で着手できない |

## M0 — 開発の土台

### ⬜ B-00 テスト戦略とCI基盤の確立　`依存: B-03`
> レビュー由来。提案書は「順序の破損は発見が遅れる」「壊れたことに気づきにくい」と
> 繰り返す。退行検知の仕組みがなければ、以降のPBIの完了条件は担保できない。

- [ ] テストフレームワークを選定（API: pytest / フロント: Jest等 / E2E: Playwright等）
- [ ] 単体・結合・E2Eの線引きを文書化した
- [ ] CIでテストが自動実行され、失敗でマージがブロックされる
- [ ] 不変条件 I-1〜I-7 を検証するテストの置き場所と書き方の雛形がある
- [ ] カバレッジの最低ラインを合意した（数値目標ではなく対象範囲の合意）

### ⬜ B-25 API共通規約の策定　`依存: B-06`
> レビュー由来。最初のCRUD（B-08）が後続の暗黙の規約になる。エラー応答・信頼境界・
> 型共有を先に決めないと、PBIごとに形式がばらつく。

- [ ] エラー応答形式を統一（401 / 403 / 404 / 409(=412楽観排他) / 422 の返し方）
- [ ] **サーバーを信頼境界とする**と明記（フロントのバリデーションはUX補助、正はAPI）
- [ ] 型/スキーマの共有方針を決定（OpenAPIからの型生成 等。TS/Pythonで真実を二重化しない）
- [ ] ページング・ソート・論理削除除外のクエリ規約を定めた

### ⬜ B-29 リポジトリ規約の整備　`依存: —`
> レビュー由来。M3のドッグフーディング前に最低限が要る。

- [ ] LICENSE を配置した
- [ ] README に開発セットアップ手順を書いた
- [ ] コミットメッセージ規約・ブランチ戦略を決めた
- [ ] CONTRIBUTING（または開発ガイド）を用意した

## 付録 — レビューで抽出した追加PBIの根拠

本ファイルの `B-00 / B-25 / B-26 / B-27 / B-28 / B-29` は提案書には無く、
「開発着手にあたって足りない部分」の設計レビューから起こした。対応関係は以下。

| 追加PBI | 元の懸念（重要度） | 要旨 |
|:---:|:---|:---|
| B-00 | 🔴 Blocker | テスト戦略が空白。不変条件・認証・rankの退行を検知する仕組みが無い |
| B-26 | 🔴 Blocker | `productId` の発生源とseedingが未定義。全設計の土台なのにPBIに無い |
| B-27 | 🔴 Blocker | 認可のブートストラップ（最初のメンバー）が未定義。全員403で詰む鶏卵問題 |
| B-25 | 🟠 設計の穴 | API共通規約（エラー応答・信頼境界・型共有）が未定。最初のCRUDが暗黙規約化する |
| B-28 | 🟠 設計の穴 | 楽観排他412の**発生後UX**が未定義。検出はするが振る舞いが無い |
| B-29 | 🟡 品質/運用 | LICENSE/README/コミット規約等が未整備。ドッグフーディング前に必要 |

既存PBIへ**注記のみ**で反映した懸念（新規PBIにはしていない）:

- **rankのフォールバック分岐**（🟠）→ B-09 の冒頭注記（Q-E）
- **論理削除の全クエリ除外**（🟡）→ B-07 の完了条件に共通化を追加
- **日付・タイムゾーン・祝日**（🟡）→ B-18 の完了条件に確認項目を追加
