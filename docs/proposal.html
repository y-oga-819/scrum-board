スクラムバックログ管理アプリ

2026-07-24  ·  実装着手のための設計仕様
Angular + Python (FastAPI) + Azure App Service + Cosmos DB + Microsoft Entra ID

00提案の概要

自律的に回っているスクラムチームが、管理コストをかけずにプロダクトバックログとスプリントを回すための小さなWebアプリを作る。

既存のスクラムツールは多機能な代わりに、入力・維持のコストが高い。本提案は機能を意図的に絞り、成熟したチームの実際の運用にモデルを合わせることで、ツールに合わせて働くのではなく、働き方にツールを合わせる方向を取る。一般的なスクラムツールの定石からいくつか意図的に外れているため、その判断の根拠を10 設計判断の記録にすべて残してある。

プロダクトスクラムバックログ管理 Webアプリケーション

実装で取り違えやすい5点
  1. スプリントを参照するのはタスクだけ。 PBIはスプリントIDを持たない（completedSprintId を除く）
  2. taskType が判別子。 pbiId が null かどうかで種別を判定してはいけない
  3. 完了タスクは動かさない。 持ち越しでも、スプリントから外すときでも、対象外である
  4. 進捗表示に警告色を使わない。 色は種別の区別にのみ使う
  5. estimate は任意。 未入力を必須エラーにも警告表示にもしない

01コンセプトと対象チーム像

誰のためのツールかを決めることが、機能を削る根拠になる。

対象とするチーム

スクラムがすでに習慣になっていて、ベロシティがおおむね安定しているチーム。こうしたチームでは見積りに時間をかけることの限界効用が下がる。ポイントを振る30分があるなら、タスクを一つ消化したほうが価値が出る局面が現実に存在する。本アプリはその判断を許容する。

対象としないチーム

立ち上げ期のチームやスクラム初学者。彼らには「未見積りの警告」「持ち越しの可視化」といった補助輪が必要だが、本アプリはそれを持たない。これは欠陥ではなくスコープの選択である。

補足

ただし「成熟チームの型に初学者チームを最初から入れてしまう」という使い方は想定内であり、否定しない。これは運用の工夫であってアプリの機能ではない。

設計原則

迷ったときはこの3つに戻る。新機能がこれに反するなら、その機能を疑う。

#原則意味するところ
P-1ルールで縛らず、事実を見せるツールは正しい振る舞いを強制しない。事実を可視化し、判断はチームに返す。「またいだスプリント数を表示する」は原則に合う。「3スプリント超えたら登録をブロックする」は合わない
P-2管理コストを下げるスクラムの原則よりも、目の前のユーザーストーリーの実現に集中できることを優先する。原則からの逸脱は、それが管理コストを下げるなら妥当な最適化とみなす
P-3後から復元できない情報だけを先に持つ機能の取捨選択の基準。あとから追加してもデータの履歴を失わないものは、後回しにしてよい

中核となるモデル

本アプリを他のバックログツールと分けている最大の特徴は、PBIは複数スプリントにまたがってよいが、スプリントに属するのはタスクだけという点にある。PBI自身はスプリントへの参照を持たない。

この構造から、次の3つが同時に成立する。

  • 大きなPBIを分割せずに扱える — 現実の運用に合わせられる（P-2）
  • スプリントバックログは100%消化を目標にできる — またいでいるPBIでも、今スプリントに入れたタスクは今スプリントで終わる想定になる
  • 過去スプリントは実績のみを表す — 完了率は常に100%になる。これは予実管理をしないという意思表示である

03画面構成

スクラムイベントごとに画面を作らない。画面は2つ、モードで切り替える。

イベントごとに専用画面を用意すると、実体は同じデータなのに「どれを開けばいいのか」を毎回考えることになる。イベントで変わるのは操作の重さであって、データではない。

イベント × 画面の対応

イベント画面操作の性質主な操作
リファインメントA書くPBI作成・分割・並び替え、完了条件の記入
スプリントプランニングA（右ペイン）選ぶPBI／タスクをスプリントへ、チームタスク追加
デイリースクラムB動かすカード移動、ブロック、アジェンダ・議事録
スプリントレビューB見せる完了分の確認、フィードバックをPBI化
レトロスペクティブB見る前回NextActionの確認（記入は対象外）

プランニングモード（画面A）

右ペインにスプリントがスライドインする。新しい画面ではなく画面Aのモードである。

重要

UIとデータモデルは一致させなくてよい。 ユーザーの体験は「PBIをスプリントに入れる」だが、実際に起きるのは「配下タスクに sprintId が付く」ことである。表示はPBI単位でグルーピングし、データはタスク単位で持つ。

スプリント画面の構成

04ドメインモデル

スプリントを持つのはタスクだけ

このモデルで最も重要な一行。PBIはスプリントへの参照を持たない。 「PBIが今スプリントに参加している」という状態は、配下タスクに sprintId = S のものが1件以上あることと同義であり、導出できる。

フィールド可変性意味
task.sprintId可変（完了で事実上凍結）今どのスプリントで取り組むか。null は「バックログで待機中」
task.completedAt不変完了日時。バーンダウンの再現に使う
pbi.completedAt不変PBIの完了日時
pbi.completedSprintId不変ベロシティの計上先。日付から逆引きしないのは、スプリント期間を後から修正すると過去のベロシティが書き換わるため

導出できるもの（保持しない）

知りたいこと導出方法
PBIが今スプリントにいるか配下タスクに sprintId = S が1件以上あるか
またいだスプリント数配下タスクの sprintId の distinct 件数
タスクが完了したスプリントsprintId そのもの（完了タスクは持ち越されないため凍結している）

タスクの3つの居場所

状態表示場所
taskType='pbi'、sprintId ありスプリント画面のボード／バックログ画面のPBI配下
taskType='pbi'、sprintId=nullバックログ画面のPBI配下のみ（待機中）
taskType='team'、sprintId=nullバックログ画面の「未割当のチームタスク」
なぜ専用セクションが要るか

チームタスクは親PBIを持たないため、スプリントから外すとどの一覧にも現れずデータが不可視になる。削除ではなく「未割当」として置き場所を与える。データが見えなくなることは、このアプリで唯一許容できない失敗である。

状態遷移

不変条件

単一のバリデーション関数に集約すること。ここを破るとタスクがどの一覧にも表示されずに消える。

#条件
I-1status != 'done' のとき completedAt は必ず null
I-2done にした時点で completedAt を記録。取り消し時は null に戻す
I-3taskType = 'pbi' のとき pbiId は必須
I-4taskType = 'team' のとき pbiId は null。判別はフィールドの有無ではなく taskType で行う
I-5完了タスクは持ち越し・除外の対象にしない。sprintId を変更しない
I-6PBIを done にできるのは配下のPBIタスクがすべて done のときのみ（警告に留め、強制はしない — P-1）
I-7PBI完了時、completedSprintId には配下タスクのうち最後に完了したタスクの sprintId を記録する（配下タスクが1件もない場合のみ、完了操作時点のアクティブなスプリント）

05進捗の見せ方

デイリースクラムで「このペースで計画通り終わるか」を判断するための計器。

2本に分ける理由

進捗表示には性質の異なる2つの問いが混ざっている。1本の積み上げバーに載せると、どちらとしても読めなくなる。

  • Q1「計画通り終わりそうか」 — 時間との対比が要る。左から右へ伸びるべきもの
  • Q2「計画外に食われていないか」 — 構成比。伸びるものではない

さらに、チームタスクを分母に含めると障害対応を追加した瞬間に達成率が下がる。何もサボっていないのにバーが後退する計器は信用されない。

採用する形

要素定義
計画タスクsprintId = S かつ taskType = 'pbi'
チームタスクsprintId = S かつ taskType = 'team'
完了status = 'done'
マーカー位置経過営業日 ÷ 総営業日。暦日で計算すると週末に必ず遅れて見えるため営業日で数える
分母の増加について

作業が進んで解像度が上がれば、PBIのタスクはスプリント中に追加される。これは健全な進行であり、異常ではない。したがって分母が増えて達成率が下がることは正常な挙動として受け入れる。

「当初は18件だった」という基準値は持たない。判断に必要なのは2本の長さの対比とマーカーとの位置関係であり、基準値がなくても成立する。

やらないこと

遅れているときにバーを警告色にする、チームタスクの比率が閾値を超えたら色を変える、といった機能は実装しない。警告を避けるためにチームタスクをPBIタスクとして登録する、という数字合わせを誘発する。色は種別の区別にのみ使い、判断はチームが行う（P-1）。

バーンダウンへの拡張余地

createdAt（共通フィールド）と completedAt が揃っているため、任意の日の残件数を後から計算できる。

D日の残数 = createdAt <= D かつ (completedAt が null または completedAt > D) の件数

スプリント中に追加されたタスクも「その日に線が上がる」形で正しく再現される。日次スナップショットを持たずにバーンダウンを後付けできるため、初期スコープから外している（P-3）。

06データモデル（Cosmos DB）

コンテナ構成

単一コンテナ／パーティションキー /productId。理由は2つある。

  • コスト — コンテナごとにスループットを割り当てると最低400 RU/s。無料枠は1000 RU/sなので、3コンテナ作った時点で課金が始まる
  • トランザクショナルバッチ — 同一論理パーティション内なら複数アイテムの一括更新が原子的に行える。並び替えとスプリント終了処理で効く

  "isDeleted": false,        // 論理削除
  "createdAt": "2026-08-03T09:12:00Z", "createdBy": "<entra oid>",
  "updatedAt": "2026-08-05T14:02:00Z", "updatedBy": "<entra oid>"

User / Migration（_system パーティション）

{ "type":"user", "productId":"_system", "id":"usr_<oid>",
  "oid":"<entra oid>", "displayName":"…", "email":"…" }

{ "type":"migration", "productId":"_system", "id":"mig_001",
  "version":"001", "appliedAt":"2026-08-01T00:00:00Z" }

user はどのプロダクトにも属さないため、productId = "_system" を予約パーティションとして設ける（D-21）。コンテナを増やさずに置き場所を作れ、id = usr_<oid> によりトークンの oid からポイントリード（約1 RU）で引ける。

member も同様に id = mbr_<oid> とする。これにより認可チェックが毎リクエスト・ポイントリード1件で済む。最頻出の処理が最も安い操作になる。

予約語

_system は productId として払い出さない。プロジェクト作成機能（B-32）でもこの値を弾くこと。

並び替え（rank）

設計上もっとも失敗しやすい箇所。パーティションキーより注意を要する。順序は要素間の相対的な関係なのに、ドキュメントDBは各要素を独立に保存するため、相対情報を絶対値に落とす必要がある。どの方式にも代償がある。

方式1回の移動で更新される件数壊れ方
整数 order後続すべて壊れないがRUを浪費する。100件並ぶと100回書き込み
浮動小数 (前+後)/21件同じ隙間に約50回連続挿入すると精度が尽き、順序が不定になる。リバランスするまで直らない
文字列ランク（fractional indexing）1件壊れない。同じ隙間への連続挿入でキーが1文字ずつ伸びるだけ

採用する仕様

項目決定理由
方式文字列ランク（fractional indexing）選定軸は実装量ではなく壊れ方。順序の破損は発見が遅れる部類で、「並び替えたのに戻る」という報告から原因に辿り着くまでが長い
実装ライブラリを使う（fractional-indexing はPython・JSの双方にある）先頭・末尾・キー枯渇の境界条件を誤ると順序が壊れ、しかも壊れたことに気づきにくい
文字集合Base36（0-9a-z）大文字小文字が混ざらないため、Z と a の比較順という不確実性が原理的に発生しない
ソートORDER BY c.rank, c.id2人が同じ位置に同時挿入すると文字列ランクでも同一キーが生まれる。ULIDの id をタイブレーカーにすれば全端末で同じ並びになる
生成場所サーバー側。APIには前後の要素IDを渡すアルゴリズムが1箇所に閉じ、フロントを差し替えても挙動が変わらない
着手前に検証すること

Cosmos DBの文字列比較のルールはドキュメント上明示が薄い。大文字小文字を区別しない、あるいはカルチャ依存の比較だった場合、並びが静かに壊れる。B-16の最初の作業として、実データを10件ほど投入し ORDER BY の結果が辞書順と一致するか確認すること。

この検証が通らなければ、浮動小数＋定期リバランスに切り替える。数値比較なのでこの不確実性がない。リバランスは全件更新になるが、同一パーティションのためトランザクショナルバッチ1回で済む。

rankのスコープ

タスクの並び順はバックログ画面（PBI配下）とボード（列内）の両方で使われる。同じ rank を共有するため、ボードで並び替えるとバックログ画面のPBI配下の順序も変わる。これは仕様として受け入れる。フィールドを分けると二重管理が復活するため、「タスクの実施順は1つ」と定義する。

運用上の設定

項目方針理由
同時編集_etag による楽観的排他。更新時に If-Match、412なら再取得朝会で複数人が同時にボードを触る。後から入れると全API改修になる
削除論理削除（isDeleted）誤操作の復旧価値が高く、この規模ならデータ量は問題にならない
インデックスdescription memo minutes を除外パスに指定既定で全プロパティにインデックスが張られる。長文を除くと書き込みRUが目に見えて減る
画像Blob Storageに置きURLのみ保持論理パーティションの上限20GBを守る
採用しない構成

Cosmos DBの定石である「関連データの埋め込み」（タスクをPBIドキュメント内に持つ）は採用しない。①「スプリント単位でタスクを取得」がPBI全走査になる ②複数人が別々のタスクを動かすと同一ドキュメントへの書き込みが競合する ③チームタスクは親を持てない — の3点による。

07主要フロー

スプリントプランニング（画面A・右ペイン）

「タスク分解」タスクの意味

タスクが0件のPBIをスプリントに入れたとき、システムは「タスク分解」というタスクを1件生成する。これは辻褄合わせではなく、「やる作業はあるが、まだ分解できていない」という実在の状態を最小限の形で表したものである。その場で分解すれば即座に完了にでき、後回しにするならそれ自体がスプリント中の作業になる。

この規則により、「タスクが無いのにスプリントにいるPBI」という状態が構造的に存在しなくなる。

スプリントから外す

持ち越しとまったく同じ規則で書ける。

sprintId = S かつ status != 'done' のタスク  →  sprintId = null

完了タスクは動かさない。 スプリント2で終わらせた作業は、PBIを外してもスプリント2の実績である。外した結果 sprintId = null で残るタスク（「タスク分解」を含む）は、バックログで待機中の正常な状態であり、次にそのPBIを取り込んだときそのまま再利用される。

スプリント終了処理

持ち越しはここに集約する。複雑さは頻度の低い操作に寄せるという方針による。

# 1. 未完了タスクを次スプリントへ（完了タスクは動かさない）
UPDATE task
   SET sprintId = <nextSprintId>
 WHERE productId = <pid> AND sprintId = <closingSprintId>
   AND status != 'done'

# 2. スプリントを締める
UPDATE sprint SET status = 'closed'

#決定却下した案理由
D-01 画面はイベント別に作らず2画面＋モード イベントごとに専用画面 実体は同じデータの見せ方の違い。専用画面にすると「どれを開くか」が毎回発生する
D-02 PBIが複数スプリントにまたがることを許容 1スプリントで完了する粒度を強制 スクラムの原則ではあるが現実には守れない。分割を強制するより、目の前の実現に集中させて管理コストを下げる（P-2）
D-03 チームタスクを taskType で明示的に区別 ① pbiId が null かで判別
② スプリントごとに「チーム運営PBI」を自動生成		 ①Cosmos DBはスキーマレスのため「未設定」と「バグで書き損ね」が区別できない ②結局は特別扱いのフラグが必要になり、判別子を持つのと変わらない
D-04 タスクが sprintId を持つ タスクはスプリントを持たず、所属PBIから導出する 持たせることで①ボード取得が1クエリになる ②チームタスクの非対称が解消する ③PBIの中で今スプリントにやるタスクを表現できる。これによりまたいでいるPBIがあってもスプリントバックログの100%消化を目標にできる
D-05 過去スプリントの完了率は常に100%。持ち越し数を記録しない スプリント締め時に carriedOverCount を記録 過去スプリントは予実管理ではなくベロシティ計測のためにある。タスク数は粒度も難易度もばらつくため、そもそも計測指標として不適
D-06 estimate は任意項目。合計ポイントを前面に出さない プランニング画面に合計ポイントを常時表示 安定したチームではポイントを振る限界効用が下がる。未見積りだと常に0と表示され「振れ」という無言の圧力になる（P-1）。ただしフィールドは残す — 無い項目は後から遡って埋められない（P-3）
D-07 タスクの依存関係の可視化をスコープ外とする 依存グラフの描画 実装コストが高い割に、並び順＋ブロック中フラグで大半が足りる。後から足しても過去データを失わない（P-3）
D-08 単一コンテナ／PK /productId エンティティごとにコンテナを分割 コンテナごとに最低400 RU/s。無料枠1000 RU/sを3コンテナで超える。加えて同一パーティション内のバッチ更新が使えなくなる
D-09 タスクをPBIに埋め込まない Cosmos DBの定石どおり子を埋め込む スプリント単位の取得がPBI全走査になり、複数人の同時更新が同一ドキュメントで競合する。チームタスクは親を持てない
D-10 Easy AuthではなくMSAL＋JWT検証 App Service Easy Auth Easy Authはローカル実行時に認証が効かずモックが必要になる。MSALならローカルでも本番と同じ経路を通せる。※リダイレクトURIは両方登録し切替可能にしておく
D-11 PBIはスプリント参照を持たない（task.sprintId に一本化） PBIに currentSprintId と sprintIds[] を持たせる 「PBIが今スプリントにいる」は配下タスクから導出できるため二重管理になる。持たせないことで、スプリント終了処理からPBI更新が消え、守るべき不変条件が1つ減る。唯一導出できない「タスク0件でスプリントにいるPBI」はD-15で解消している
D-12 タスクは completedAt を持ち、完了スプリントIDは持たない task.completedSprintId に完了スプリントを刻印 完了タスクは持ち越されないため sprintId は完了時点で凍結する。つまり完了スプリントIDは常に sprintId と一致する冗長フィールドになる。completedAt にすれば日単位の情報が増え、バーンダウンの後付けが可能になる。※pbi.completedSprintId は日付逆引きだとスプリント期間の修正で過去が書き換わるため保持する
D-13 進捗は件数主役の2本バー。「当初件数」は持たない ① 4区分の積み上げバー1本
② スプリント開始時の件数を記録して「当初18→+4」と表示		 ①「計画通り終わるか」と「計画外に食われていないか」は別の問いで、同じ軸に載せると両方読めなくなる。またチームタスクを分母に含めると障害対応の追加で達成率が下がる ②判断に必要なのは2本の長さの対比とマーカーとの位置関係であり、基準値がなくても成立する
D-14 プランニングはバックログ画面の右ペイン スプリント画面から「PBIを追加」する 主役は選ぶ対象であるバックログの側。優先順位順の一覧を崩さず上から引くのはプル型というスクラムの動きそのもの。スプリント画面は「動かす」ことに最適化してあり、探して選ぶ操作を混ぜるとデイリーで重くなる。※スプリント中の差し込み用に同じパネルを画面Bからも開ける
D-15 タスク0件のPBIを取り込んだら「タスク分解」タスクを自動生成 タスクのないPBIをスプリントに置けるようにする 「やる作業はあるが、まだ分解できていない」という実在の状態を最小の形で表す。その場で分解すれば即完了でき、後回しならスプリント中の作業として妥当。これで特別な状態を作らずに済む

着手順について

外部のリードタイムに依存する作業はないため、着手順を縛る制約は依存関係だけである。

M3（B-11・B-12・B-13）は他PBIの品質を担保する土台である。テスト基盤とAPI共通規約が無いままB-15以降を書くと、退行検知と規約の一貫性が後追いになり手戻りが増える。スクラム機能の作り込みに入る前に片付ける。

M1・M2が本プロジェクトの主題である（D-21）。本アプリは「Easy Authを使わないEntra IDの認証・認可」を実証するPoCを兼ねており、最も不確実な部分を最初に検証する順序を取る。Entra IDの設定漏れは後工程で分かりにくい形で表面化する（08章）ため、後回しにする理由がない。

認証と認可を分けているのが順序設計の要点である。認証（B-03・B-04）はデータストアを必要とせず、ローカルの localhost:4200 だけで検証できる。認可（B-09・B-10）は member をCosmosに持つためデータ層を要する。この境界でM1とM2を切ることで、PoCの核心に最短で到達できる。

M3の土台（テスト・API規約）はスクラム機能の作り込みに先立って必要になるが、PoC自体を無検証で進めるのは避けたいため、V-1〜V-4のテストはB-04の完了条件に含め、テスト基盤の全体構築を待たない。

アプリ登録とリソース作成は再現できる形で残すこと（09章）。一度きりの作業に見えるが、無料枠の作り直し、検証環境の追加、メンバーの増加で必ず再実行される。

完了条件の書き方について

上記の完了条件は、設計判断が実装に落ちたかを確認できる形で書いてある。たとえばB-16は「並び替えができる」ではなく「更新が1件だけ」、B-24は「バーが出る」ではなく「営業日で計算され警告色を使っていない」としている。設計と実装が乖離する典型は、機能は動くが判断の理由が失われる形なので、そこを条件に含めている。
